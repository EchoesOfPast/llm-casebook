# llm-casebook

在具体情境下，用什么方法能让大模型写出你真正想要的东西？这个项目收集答案，并且要求每个答案都附上证据。

方法不限于提示词，也包括上下文样本、多步工作流、检查脚本、采样参数、换模型和微调。先从小说写作做起，跑通后扩展到其他领域。

---

## 缘起

我在用大模型写小说时，和模型来回拉扯了几十轮。

它的毛病很典型：情绪写到一半就开始升华；堆一些和人物毫无关系的细节；把人物心理直接写成旁白，像解说比赛；用第一人称写哭得看不清东西，下一句却能看清对方下巴的肌肉；为了制造效果，悄悄改掉前文已经发生的事。

我试着用提示词一条条禁止，结果每禁掉一种，就冒出另一种。

更让我在意的是它当评判者的时候。同一段文字，它可以前一轮批评，后一轮夸成“神来之笔”，只因为我打了一个问号。关于“提示词到底有没有用”，它先说彻底无解，后来又说完全可解，每次都说得很笃定，也都说得很有道理。

但这场对话也给了我真正的启发：**模型对自己毛病的诊断，往往相当准确。**它能条理清楚地说出哪里写坏了、为什么坏，然后在下一段里照犯不误。

问题不只是模型能力不够，我们还缺两样东西：一套稳定的标准，用来判断什么是好；一批经过验证的方法，用来把“知道”变成“做到”。

## 这场对话暴露的问题

**1. 禁令治标不治本。**
禁令只描述你不要什么。把症状一个个压下去，背后的原因没动，它就会换一种症状冒出来。你想要的东西是具体的、正面的，用排除法圈不出来。

**2. 讲得流畅，不再等于对。**
过去，一个人能把事情讲清楚、讲出条理，通常说明他懂。大模型把这两件事拆开了：它可以用同样流畅、同样有说服力的语气，先后给出相反的结论。解释变得廉价以后，可信的只剩下能被重复检验的东西。

**3. 评判会被语气带偏。**
模型的评价有一部分只是用户语气的回声。用户以为自己在观察模型，其实自己也是变量之一。

**4. 模型给出的是平均，不是“这一个”。**
模型见过所有的重逢，所以它写出来的是重逢的平均样子。而写作者想要的，是只属于自己笔下人物的那一场。最打动人的细节，比如一个外号、一棵树、某个人喊吃饭的声音，只存在于具体的人那里。

**5. 经验随着对话消失，也随着模型更新过期。**
每个认真用模型写东西的人，都在私下重复同样的试错。这些经验网页一关就没了；就算记了下来，换一个模型版本，也可能不再成立。

## 初心

我不相信“提示词万能”，也不接受“AI 写不好，关掉网页自己写”。前者是盲信，后者是放弃，两者都省掉了同一件事：测量。

所以这个项目想做的是：**对每一个“我想让模型做到某件事”的情境，积累有证据的方法**。哪些有效，在哪个模型上有效，有效到什么程度；哪些无效，为什么无效。

它是开放的，因为一个人的试错积累不住，很多人的试错放在一起，才能成为后来者的起点。

## 几点思考

**呈现，不要告知。**
这是写作课上的老话，原本讲给写作者听，后来我发现它在三个地方同时成立。写小说时，解说情绪不如直接写出发生了什么；指挥模型时，讲一堆规则不如给它看一段好文字；做一个方法库时，说“这个提示词很好用”不如贴出原始输出。这个项目在形式上，就是第三种呈现。

**利用“知道”和“做到”之间的缝隙。**
模型诊断问题的能力强于它控制输出的能力。好的方法应该利用这一点：标准固定在模型之外，让模型对照检查，而不是指望它一次写对；把生成和评判拆开，不让同一段对话的气氛同时决定两者。

**判断留在人这边。**
模型擅长整理、展开、排查前后矛盾，也擅长在你给出材料后把句子理顺。但“什么是好”是某个具体的人的判断。这个项目里的每个情境都要写清楚“这是谁的口味”，因为不存在对所有人都好的写法。

**对所有判断者保持距离。**
包括模型，也包括自己。所以要固定测试输入，要盲评，要把原始输出全部公开，不只贴最好的那一次。

**证据会过期。**
模型在不断更新，今天有效的方法明天可能失效。每条记录都写明模型版本和日期，失效的标为“已失效”，保留不删。失效本身也是信息。

## 怎么运作

```
情境 (scenarios/)    想要什么效果：固定的测试输入、评判标准、口味说明
   ×
方法 (methods/)      用什么手段：提示词 → 上下文 → 工作流 → 工具 → 参数 → 模型 → 微调
   =
实验 (experiments/)  某个方法在某个情境、某个模型上的一次测试，附全部原始输出
```

同一个情境下，不同方法、不同模型的结果可以并排比较。方法的分层和使用门槛见 [methods/](methods/README.md)。

## 原则

1. 没有实验记录的方法，只能标为“待验证”。
2. 失败的结果同样收录。
3. 原始输出全部公开，每次至少 3 次。
4. 主观领域写明口味：这是谁的标准。
5. 写明模型版本和日期，定期复测。
